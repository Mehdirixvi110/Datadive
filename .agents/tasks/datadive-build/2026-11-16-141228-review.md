# Datadive marketing site — full-state semantic review

The Datadive site is a Next.js 15 App Router application that renders a dark, animated marketing home page plus a blog and optional project detail pages, all backed by Airtable through one typed server-only data-access layer and editable through a Google-auth-gated admin dashboard. The contract's headline promise — build and render with zero environment variables from committed seed data — holds: a clean `npm run build`, `npm run lint`, and `npx vitest run` all pass with no env set, and the build statically generates the home page, `/blog`, both seed posts, and five seed project detail pages. The implementation tracks the locked design closely across the Airtable boundary, audience-split caching, seed fallbacks, the two auth guards, Blob host validation, dynamic WhatsApp, and Markdown sanitization.

Watch for: slug uniqueness and auto-generation on save, which the design mandates (§13, FR-11.5), are **not** wired — the `uniqueSlug`/`slugify` helpers exist and are unit-tested but no admin action calls them (confirmed), so an admin can save two records with the same slug and make one detail page unreachable.

**Verdict**: CHANGES_REQUESTED

## High-level view

The data layer is exactly one boundary. Every Airtable call goes through `src/lib/airtable/client.ts`, which opens with `import 'server-only'`, and the public reads in `read.ts` apply publish/visibility filtering and ordering inside the DAL so a component cannot leak a draft. Caching is split by audience as specified: public reads carry `next: { revalidate: 3600, tags }`, admin reads use `cache: 'no-store'` with no tags so the dashboard is always live. All of this is confirmed in source.

Credential detection drives graceful degradation. `hasAirtableCreds()` gates whether the network is touched at all; with no creds every read returns seed, singletons fall back to the seed singleton on an empty table, lists return the real empty set, and `getReviews()` is the one deliberate exception that reinjects seed placeholders on an empty live table (FR-9.2). The `hasDetail = published && body non-empty` predicate is computed once in the mapper and reused by routing, params, and sitemap.

Auth is defense-in-depth and fail-safe. `hasAuthCreds()` (all three of `AUTH_SECRET`, `AUTH_GOOGLE_ID`, `AUTH_GOOGLE_SECRET`) is checked before any `auth()` call in middleware, both guards, and the NextAuth route, so a zero-env request to `/admin/*` redirects or 404s instead of hitting Auth.js's lazy `MissingSecret` 500. The two guards (`requireAdminPage()` redirecting, `requireAdmin()` throwing) share one allowlist check, and `withAdmin()`'s catch is narrow enough to re-throw `NEXT_REDIRECT`/`NEXT_NOT_FOUND` control flow.

Image handling stays on the Blob allowlist. Stored image URLs are Zod-validated to a same-origin path or the `*.public.blob.vercel-storage.com` host, `next.config.ts` restricts `remotePatterns` to that host with `dangerouslyAllowSVG` explicitly off, seed placeholders are committed raster PNGs, and the upload route gates on `requireAdmin()` and rejects SVG. WhatsApp links are built from the settings number and the button hides entirely when it is empty; no contact value is hardcoded in any component.

The one gap is slug handling on save. The design calls for auto-generating a slug from the title when blank and enforcing uniqueness by querying the table and suffixing `-2`, `-3` on conflict. The helpers for this are implemented and tested but never imported by an action or form, so the behavior is absent.

### Zero-env gate: build, lint, tests

A clean build (after clearing `.next` and stale processes from an earlier interrupted run) completes in ~53s and prerenders 20 pages with no env configured. `/`, `/blog`, `/sitemap.xml`, and the `/work/[slug]` and `/blog/[slug]` sets render from seed; admin routes and the three API routes are dynamic; middleware is emitted at 85.5 kB. `npm run lint` reports no ESLint warnings or errors, and `npx vitest run` passes 100 tests across 9 files (mappers, reads, writes, validation, seed, utils, require-admin, contact, admin actions) with no network. The gate is met (confirmed).

An earlier `npm run build` appeared to hang; the cause was a timed-out foreground run leaving node processes that held the `.next` lock while a second build contended. A single clean run is the real signal and it succeeds.

### Slug uniqueness and auto-generation are unimplemented

Design §13 specifies that a slug is "auto-generated from title if blank" and that "uniqueness [is] checked on save (query table; on conflict append `-2`, `-3`, …)", and FR-11.5 requires each post to have a unique, stable slug. `src/lib/utils/slug.ts` implements both `slugify` and `uniqueSlug` (with `-2`/`-3` suffixing) and `utils.test.ts` covers them, but a workspace-wide search finds no caller outside the file's own module, its re-export in `utils/index.ts`, and the tests (confirmed). `createProjectAction`/`updateProjectAction` (and the blog equivalents) validate the slug only for format via `slugSchema` and pass it unchanged to `createProject`/`updateProject`.

Two consequences follow. Because `slugSchema` has `min(1)`, a blank slug is a validation error rather than being derived from the title, so the "auto-generate when blank" behavior is absent. More importantly, nothing prevents two projects or two posts from sharing a slug. `getProject`/`getBlogPost` resolve a slug with `records.find(...)`, so the first matching record wins and the second becomes unreachable at its detail route while still sharing the `project:{slug}`/`blogpost:{slug}` cache tag, and `generateStaticParams` would emit the slug twice. The failure is admin-triggered and recoverable by editing the slug, which is why it is MEDIUM rather than HIGH, but it is a committed contract behavior that is entirely missing.

The fix is to call `uniqueSlug(desired || title, existingSlugs)` inside the create/update actions, sourcing `existingSlugs` from `getAllProjects`/`getAllBlogPosts` and excluding the record under edit, then persist the resolved slug.
